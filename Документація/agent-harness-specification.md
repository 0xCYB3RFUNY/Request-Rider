# Специфікація та Архітектура Agent Harness для Request-Rider

## 1. Контекст та Проблематика

У проєкті Request-Rider автономні LLM-агенти стикаються з чотирма фундаментальними обмеженнями згідно з моделлю **Agent Harness Construction**:
1. **Якість Action Space (Простір дій)**: Агенти часто використовують неструктуровані команди термінала (`bash`), що призводить до зависань фонових процесів, блокування портів або конфліктів середовища.
2. **Якість Observation (Спостереження)**: Вивід компіляторів, лінтерів та тестів надто розлогий, неструктурований та не містить чітких кроків відновлення після помилок.
3. **Якість Error Recovery (Контракт відновлення)**: Замість локалізації першопричини (root cause hint) агенти можуть нескінченно модифікувати код або міняти стратегію без оновлення плану.
4. **Якість Context Budget (Бюджет контексту)**: Кореневий файл `AGENTS.md` займає понад 380 КБ, що призводить до перевитрати контексту моделі, обрізання виводу та зашумлення робочої пам'яті.

## 2. Архітектура Agent Harness

```
+------------------------------------------------------------------------+
|                            AUTONOMOUS AGENT                            |
+------------------------------------------------------------------------+
         |                                                 ^
  Structured Action                                  Structured Observation
  (rr_agent_harness CLI)                             (JSON / Contract)
         v                                                 |
+------------------------------------------------------------------------+
|                        RR AGENT HARNESS CORE                           |
|  - Subsystem isolation (Go tests, Python tests, Linters, Builds)        |
|  - Diff & Scope compliance checker (Allowed vs Actual files)           |
|  - Deterministic state validation & Health-check                       |
+------------------------------------------------------------------------+
         |                                                 |
         +-------------> Target Execution Area <-----------+
                         - engine / bin / web
                         - live services (:8000, :8080, :8090)
```

## 3. Стандартизація Action Space (Простір Дій)

### 3.1. Рівні гранулярності інструментів
- **Micro-tools (Високий ризик)**:
  - Зупинка / перезапуск процесів (`engine`, `browser-worker`, `django`).
  - Зміна прав доступу, міграції бази даних.
- **Medium-tools (Основний цикл TDD)**:
  - `rr_agent_harness run-tests --suite <go|python|guards>`: запуск тільки релевантних ізольованих тестів.
  - `rr_agent_harness check-scope`: верифікація списку змінених файлів проти плану.
  - `rr_agent_harness lint`: перевірка синтаксису, `go vet`, `flake8`/`black`.
- **Macro-tools**:
  - `rr_agent_harness compliance`: повний фінальний комплаєнс-аудит (тести + git diff + guard-перевірки).

## 4. Контракт Спостереження (Observation Contract)

Кожна відповідь harness зобов'язана повертати детерміновану структуру:

```json
{
  "status": "success | warning | error",
  "summary": "<Одне речення з результатом перевірки>",
  "details": {
    "passed": 12,
    "failed": 0,
    "failures": []
  },
  "root_cause_hint": "<Підказка щодо першопричини або null>",
  "safe_retry_instruction": "<Безпечний наступний крок або команда для повтору>",
  "explicit_stop_condition": "<Критерій, за якого агент зобов'язаний зупинитися>",
  "next_actions": [
    "Виправити синтаксис у файлі X",
    "Перезапустити перевірку через harness"
  ],
  "artifacts": [
    "file:///path/to/report"
  ]
}
```

## 5. Контракт Відновлення (Error Recovery Contract)

1. **Root Cause Hint**: При падінні тесту harness ізолює стек виклику і формулює сутність помилки (наприклад: *неканонічний вердикт у рядку 85* або *відсутній бінарник browser-worker*).
2. **Safe Retry Instruction**: Заборонено хаотичне редагування сусідніх модулів. Harness вказує точну команду повтору (наприклад, `go test ./engine -run TestSpecific`).
3. **Explicit Stop Condition**: Якщо помилка вимагає зміни публічного контракту API або нерозв'язна без втручання оператора, агент зобов'язаний зупинитись і надати звіт `CONFLICT_DETECTED` або запросити уточнення.

## 6. Оптимізація Context Budget (Стратегія для AGENTS.md)

1. **Ядро контракту (Invariant Core)**: Залишається в системному промпті або лаконічному `AGENTS.md` (до 150 рядків):
   - Статус обов'язковості (Contract Status).
   - Жорсткий життєвий цикл (8 кроків).
   - Формат фіксації плану.
   - Stop-on-conflict принцип.
2. **Динамічні навички (On-demand Skills & Refs)**:
   - Детальні правила реєстрів вердиктів винести в `Документація/reconciliation-rules.md`.
   - Інваріанти розкладки веб-інтерфейсу винести в `Документація/layout-invariants.md`.
   - Специфікації інструментів винести в `Документація/tool-matrix.md`.
3. **Компактифікація (Compaction at Phase Boundaries)**:
   - Сесії фіксують артефакти у `SESSION-CLAIMS.md` та `DEVELOPMENT_LOG.md` короткими дельтами, уникаючи повторення всього історичного логу в контексті.

## 7. Guard-тести та Автоматизований Контроль

Harness інтегрує guard-перевірки:
- `test_no_untracked_verdict_drift`: заборона хибних написань вердиктів (`улушшено` vs `улучшено`).
- `test_plan_scope_compliance`: виявлення файлів, змінених поза затвердженим планом.
- `test_clean_environment`: перевірка відсутності «завислих» або незакритих процесів/портів.
