# Рекомендації з безпеки

RequestRider призначений для локального QA, аналізу HTTP-трафіку та
дозволеного тестування систем, якими ви володієте або на перевірку яких маєте
явний дозвіл. Жоден окремий захисний захід не гарантує абсолютної
анонімності чи безпеки: використовуйте багаторівневу ізоляцію, мінімізуйте
збереження даних і контролюйте кожну ціль тестування.

## 1. Захист робочого хоста

### Шифрування диска

Робочий хост має використовувати повне шифрування диска. Для Kali Linux
рекомендований варіант — **LUKS** із шифруванням розділу або всього диска.
Шифрування захищає дані, якщо пристрій буде втрачено або викрадено, але не
захищає вже розблоковану систему від шкідливого процесу.

Особливо важливо захищати:

- `data/ca/ca.key` — приватний ключ локального MITM CA;
- SQLite-базу History;
- експортовані JSON/CSV/HTML-файли;
- cookies, Authorization-заголовки та тіла запитів;
- API-ключі LLM-провайдерів і журнали роботи.

Не комітьте `data/ca/ca.key`, локальні бази, secrets або експорти до Git,
хмарних сховищ чи систем звітності без попереднього очищення.

### Пароль і блокування

Використовуйте довгий унікальний пароль для шифрування диска та окремий
пароль для облікового запису користувача. Не використовуйте один пароль для
LUKS, Linux, VPN, SSH і LLM-провайдера.

Рекомендується:

- використовувати password manager;
- увімкнути автоматичне блокування екрана;
- не залишати розблокований хост без нагляду;
- застосовувати MFA для VPN, пошти, GitHub та інших зовнішніх сервісів;
- регулярно оновлювати Kali Linux, Docker, браузер і залежності проєкту.

### Розмежування прав

Працюйте під звичайним користувачем, а не під `root`. Команди з `sudo`
виконуйте лише тоді, коли вони дійсно потрібні. Не запускайте RequestRider,
Django або Go engine від імені `root`.

Група `docker` фактично надає високі привілеї, близькі до root-доступу на
хості. Додавайте користувача до цієї групи лише на ізольованій тестовій
системі та не вважайте Docker-контейнер повним бар’єром від компрометації
хоста.

## 2. Мережевий захист

### VPN і kill switch

Якщо тестування має виконуватися через VPN, налаштуйте VPN **до** запуску
RequestRider. Kill switch має блокувати весь вихідний трафік при втраті VPN,
а не лише показувати повідомлення про розрив.

Перевірте окремо:

1. що VPN піднятий;
2. що маршрут за замовчуванням проходить через VPN;
3. що DNS-запити не витікають через інший інтерфейс;
4. що після розриву VPN звичайний інтернет недоступний;
5. що після відновлення VPN трафік повертається через очікуваний інтерфейс.

Tor і VPN — різні механізми. Tor не замінює firewall або kill switch, а VPN
не гарантує анонімність. Не покладайтеся на один канал захисту.

### Firewall

Налаштуйте firewall відповідно до власної моделі загроз. Для робочого
ноутбука без потреби в серверах рекомендована політика:

- дозволяти вихідні з’єднання лише за необхідності;
- **блокувати всі вхідні з’єднання за замовчуванням**;
- дозволяти loopback-трафік;
- дозволяти встановлені та пов’язані з’єднання;
- окремо дозволяти VPN;
- не відкривати SSH, Docker API або панель керування назовні без потреби.

Локальні порти RequestRider мають бути доступні лише на loopback:

```text
127.0.0.1:8000  Django UI
127.0.0.1:8080  passive MITM proxy
127.0.0.1:8081  Go engine API
127.0.0.1:9050  локальний SOCKS5 Tor
```

Не змінюйте `127.0.0.1` на `0.0.0.0`, якщо немає чіткої причини, firewall-
правил і додаткової автентифікації. UI та engine не мають бути доступні з
локальної мережі або Інтернету за замовчуванням.

## 3. Віртуальна машина та ізоляція

Для тестування рекомендовано використовувати окрему віртуальну машину. У
ній можна розмістити:

- Kali Linux або іншу спеціалізовану ОС;
- RequestRider;
- Docker Engine і Docker Compose;
- локальне Python-оточення web-компонента;
- Go engine;
- контейнер Tor;
- окремий браузер із налаштуванням proxy.

Віртуальна машина зменшує вплив помилок конфігурації, але не є абсолютною
гарантією безпеки. Підтримуйте гіпервізор і guest OS оновленими та не
вмикайте спільні папки, clipboard або USB passthrough без необхідності.

Рекомендований підхід:

1. створити чистий snapshot перед тестуванням;
2. використовувати окремого користувача та окремий профіль браузера;
3. не монтувати домашній каталог хоста в контейнер;
4. не передавати в контейнер Docker socket без крайньої необхідності;
5. після завершення видалити або зашифрувати артефакти тестування;
6. повернути VM до чистого snapshot, якщо тестувалася недовірена система.

## 4. Docker Compose і компоненти RequestRider

Docker Compose розділяє основні компоненти на сервіси:

```text
web    -> Django UI і SQLite gateway
engine -> Go engine і passive MITM proxy
tor    -> SOCKS5 Tor upstream
```

У Compose engine використовує маршрут `tor:9050` усередині Docker-мережі.
Це відрізняється від локального запуску, де використовується адреса на
кшталт `127.0.0.1:9050`.

Перед запуском перевіряйте:

```bash
docker compose config
docker compose ps
docker compose logs --no-color tor
curl http://127.0.0.1:8081/health
```

У логах Tor очікуйте завершення bootstrap із повідомленням:

```text
Bootstrapped 100% (done)
```

Потім перевірте маршрут через UI або engine. Адреса маршруту в Docker має
бути `tor:9050`, а зовнішня IP-адреса повинна відрізнятися від прямої
адреси хоста.

Порти Compose публікуйте лише на `127.0.0.1`. Не публікуйте `9050`, `8080`,
`8081` або `8000` на всі мережеві інтерфейси без окремого firewall і
контролю доступу. Якщо host-порт уже зайнятий системним Tor, не запускайте
другий Tor на тому самому порту: або зупиніть непотрібний сервіс, або
використайте тимчасовий локальний порт для діагностики.

Контейнер не повинен розглядатися як повна межа безпеки. Закріплюйте
версії образів у контрольованому середовищі, регулярно оновлюйте базові
образи та не запускайте невідомі образи з неперевірених registry.

## 5. Python, Go і локальні секрети

Для web-компонента використовуйте окреме Python virtual environment. Не
встановлюйте залежності проєкту глобально, якщо цього можна уникнути.
Залежності слід оновлювати контрольовано та перевіряти перед оновленням
production-подібного середовища.

Не зберігайте в коді або session-файлах:

- VPN-паролі;
- приватні ключі;
- API-ключі;
- cookies живих облікових записів;
- токени доступу;
- повні дані недозволених або сторонніх цілей.

Перед передачею логів, скриншотів або експорту іншій людині видаліть
Authorization, Cookie, Set-Cookie, API keys, персональні дані й інші секрети.

## 6. Безпечна робота з passive MITM

Passive MITM proxy бачить HTTP-запити, HTTPS після встановлення локального CA,
заголовки, cookies та тіла. Встановлюйте `data/ca/ca.crt` лише у спеціальний
тестовий профіль браузера або VM.

Після тестування:

- видаліть CA з довіреного сховища тестового профілю, якщо він більше не
  потрібен;
- не встановлюйте локальний CA у повсякденний браузер;
- не використовуйте живі банківські, поштові або адміністративні сесії;
- очистіть Traffic, History та експортовані файли;
- зберігайте `data/ca/ca.key` окремо й обмежте права доступу.

Запити Firefox Push Service та інші службові запити браузера можуть
потрапляти до Traffic. Це не означає, що вони є частиною тестованого
застосунку. Використовуйте окремий профіль браузера та за потреби вимикайте
непотрібні фонові служби.

## 7. Межі дозволеного тестування

Перед запуском Repeater, Intruder, Target, OSINT або Scanner:

1. зафіксуйте письмовий дозвіл;
2. визначте дозволені домени, IP, порти та часові межі;
3. узгодьте максимальну кількість запитів і затримку;
4. виключіть production-дані, персональні облікові записи та сторонні
   інтеграції;
5. підготуйте контакт для аварійного припинення тестування;
6. зупиніть тестування одразу після виходу за межі scope.

Наявність Tor, VPN, Docker або VM не робить несанкціоноване тестування
дозволеним і не знімає відповідальності оператора.

## 8. Мінімальний checklist перед запуском

- [ ] Диск хоста зашифрований через LUKS або еквівалентний механізм.
- [ ] Увімкнено сильний пароль і автоматичне блокування.
- [ ] Працює звичайний користувач без зайвих привілеїв.
- [ ] VPN і kill switch перевірені, якщо вони потрібні для сценарію.
- [ ] Вхідні з’єднання firewall заблоковані за замовчуванням.
- [ ] RequestRider доступний лише через loopback.
- [ ] Використовується окрема VM або інше ізольоване середовище.
- [ ] Docker Compose не запущений паралельно з локальним запуском.
- [ ] Tor досяг `Bootstrapped 100% (done)`.
- [ ] Перевірена зовнішня IP-адреса через поточний маршрут.
- [ ] Встановлено тестовий CA лише в окремий браузерний профіль.
- [ ] Scope і дозвіл на тестування зафіксовані.
- [ ] Секрети не потрапляють у Git, логи або експорти.

Цей документ є загальними рекомендаціями з операційної безпеки, а не
юридичною, мережевою чи криптографічною гарантією. Остаточна конфігурація
має відповідати вашій моделі загроз, політикам організації та вимогам
законодавства.
